# Функциональные требования

Приоритет: **MoSCoW**. Заказчик — первый пользователь-разработчик; продукт рассчитан на **нескольких тренеров** в одной установке без смешивания данных.

## Must

- **ADMIN-001:** Роль **`platform_admin`**: доступ к **разделу администрирования**. **Все** пользователи — **тренеры** со своим **`trainerId`**; учёток «только админ» **без** тренерства **нет**. Отдельный интерфейс раздела. Содержимое: создание и сопровождение **других** учёток тренеров (с `trainerId` и сидом упражнений), блокировка, сброс пароля. Через этот UI **нельзя** назначать или снимать **`platform_admin`** (см. **ADMIN-004**). **Без** доступа к клиентам, планам и фактам **чужих** `trainerId` (кросс-тенантно).
- **ADMIN-002:** Создание **новой учётки тренера** (идентификатор — обычно **email** + первоначальный пароль или «задать при первом входе»); в той же **транзакции** — **`trainerId`** и загрузка **сида упражнений** (см. `EX-000`).
- **ADMIN-003:** **Список** учёток тренеров (минимум: идентификатор, статус активен/заблокирован); **блокировка** и **разблокировка**; **сброс пароля** (новый временный пароль или одноразовая ссылка — по реализации).
- **ADMIN-004:** Роль **`platform_admin`** **не** назначается и **не** снимается через **UI приложения**; изменение — только **вне** приложения (миграция, CLI, переменные окружения / bootstrap, согласованная процедура деплоя или ручная правка данных).
- **AUTH-001:** **Вход** и **выход**; **сессия** с безопасным хранением токена/куки (без известных антипаттернов). Одна сессия на учётку; **каждая** учётка — тренерская (**`trainer`** + **`trainerId`**). **Раздел администрирования** — только при наличии **`platform_admin`**.
- **AUTH-002:** **Смена пароля** залогиненным пользователем.
- **TENANT-001:** **Изоляция по тренеру:** сущности `Client`, `PlannedWorkout`, `WorkoutSession`, **Exercise** и прочие доменные записи принадлежат ровно одному `trainerId`. Любой **тренерский** API **фильтруется** по текущему тренеру; чужие `id` — 404/403 без утечки факта существования. **Админ** не обходит изоляцию ради чтения чужих тренировочных данных.
- **CLIENT-001:** CRUD клиентов **в рамках аккаунта** тренера (минимум: имя; опционально контакты/заметки — по желанию).
- **EX-000:** **Справочник упражнений** тренера: создание и редактирование; **исключение из рабочего списка** — через **мягкое удаление** (архивация): запись **не** показывается при выборе упражнения для **новых** планов и фактов, но **ссылки** `exerciseId` в уже сохранённых планах и фактах **остаются** валидными, история и сравнения не ломаются. Реализация: поле вроде **`archivedAt`** / **`isArchived`** у `Exercise`; **hard delete** строки в MVP **не** применяем. При **создании** **новой** учётки тренера **из админ-раздела** копируется **стартовый сид-лист** в `Exercise` с данным `trainerId`.
- **SPLIT-001:** У клиента доступен **сплит как свободные теги** типа дня: заранее заведённый пул (для автодополнения) и/или ввод **нового тега** при создании плана/факта. «Аналогичная» прошлая тренировка — с тем же **строковым тегом** у того же клиента (без понятия «номер дня в цикле»).
- **PLAN-001:** Создание и редактирование **планов** тренировок **наперёд**: у клиента допускается **произвольное число** будущих планов (логика «следующая тренировка», затем ещё одна за ней и т.д.). У **каждого** плана: **плановая дата** (для сортировки «что дальше» и привязки к календарю) и **тег** типа дня. *(Если дата временно не нужна — допускается порядковый номер/очередь; зафиксировать при разработке UI.)*
- **PLAN-002:** В плане: упражнения из справочника (**только не архивные**), порядок, для каждого упражнения — **запланированные** подходы (число подходов, целевые повторы, целевой вес; расширения — отдых, RPE — по мере необходимости).
- **PLAN-003:** **Список предстоящих** планов клиента: все с **плановой датой ≥ сегодня** (или статусом «запланировано»), сортировка от ближайшей; возможность открыть любой из них.
- **FACT-001:** **Жизненный цикл** тренировки: (1) **Запланированная** — `PlannedWorkout` (см. PLAN-*). (2) **Старт** — тренер переводит план в **текущую** тренировку: создаётся сессия в статусе **«в процессе»** (`in_progress`) с тем же `clientId`, **`splitTag`**, фиксируется **время старта**; опциональная связь **`plannedWorkoutId`**. Допускается **старт с нуля** без плана — сессия без `plannedWorkoutId`. (3) Пока **в процессе**: фиксируются подходы; часть запланированных упражнений может остаться **невыполненной**; можно добавить **внеплановые** упражнения и подходы. (4) **Завершение** — сессия переходит в статус **«завершена»** (это и есть **факт** в истории), фиксируется **время окончания**; после этого работают сравнения план↔факт и «аналогичная прошлая».
- **FACT-002:** Редактирование сессии **в процессе** «в зале»: добавить/убрать упражнение, изменить порядок, число подходов, веса, повторы — без лишних шагов; автосохранение по выбору реализации.
- **FACT-003:** У одного **тренера** может быть **несколько** одновременно **текущих** (`in_progress`) сессий для **разных** клиентов; **старт** и **завершение** любой из них **не блокирует** остальные.
- **FACT-004:** На пару **`trainerId` + `clientId`** в один момент времени — **не более одной** сессии `in_progress` (новый старт блокируется или предлагает завершить/отменить текущую — выбрать в UX).
- **CMP-001:** **Сравнение план ↔ факт** для тренировки, начатой **с плана**: контекст **`PlannedWorkout`** vs связанная **завершённая** `WorkoutSession` (таблица, split-view, подсветка отклонений — в дизайне). Если тренировка начата **без плана**, сравнение «план ↔ факт» для этой сессии не применимо (остаются история и сравнение с прошлой аналогичной).
- **CMP-002:** **Сравнение с прошлой аналогичной** **завершённой** тренировкой (тот же клиент, тот же **тег**): хотя бы ключевые метрики по совпадающим упражнениям или сводка по объёму/весам.
- **HIST-001:** **История по упражнению** в разрезе клиента: хронология **завершённых** сессий с фактическими подходами (и при необходимости запланированными на те же даты).
- **WEIGHT-001:** Все **веса** в планах, **сессиях** и истории — в **килограммах** (дробные значения допустимы); единый формат в API и БД без поля «единица измерения» в MVP.
- **UX-001:** **Переключение контекста клиента** (карточка/список): не более 1–2 действий из типичных экранов; желательны «недавние» и поиск по имени.
- **UX-002:** **Переключение между текущими тренировками** (`in_progress`, **разные** клиенты): не более 1–2 действий; в интерфейсе виден **список активных** тренировок (минимум: имя клиента; опционально тег дня / время старта).

## Should

- **ADMIN-BOOT-001:** Первые пользователи (в т.ч. с **`platform_admin`**) создаются **вне обычного UI** (миграция, CLI, env при первом деплое, одноразовый setup с последующим отключением) — без «курицы и яйца». Каждая такая (и любая последующая) учётка **обязательно** тренер: **`trainer`** + **`trainerId`** + сид; **`platform_admin`** при необходимости выставляется **только** этим же **внешним** способом, **не** через админ-раздел. Дальнейшие учётки тренеров создаются **из раздела администрирования**.
- **DASH-001:** Список последних тренировок по клиенту с фильтром по **тегу** типа дня.
- **DATA-001:** Резервная копия данных (экспорт файла / дамп БД) — важно для личного инструмента.

## Could

- **AUTH-REG-001:** Публичная **саморегистрация** тренера (когда понадобится вместо или в дополнение к выдаче учёток админом).
- **FACT-CANCEL-001:** Отмена **текущей** сессии без записи в историю как «факт» (или запись со статусом «отменена» — по желанию).
- **EX-ARCH-UI-001:** Экран «архив упражнений» с возможностью **вернуть** упражнение в рабочий список (снять архивацию).
- **AUTH-EMAIL-001:** **Самостоятельное** восстановление пароля тренера по **email** (без участия админа).
- **AUTH-OAUTH-001:** Вход через OAuth (Google и т.д.) для тренеров или админов.
- **TEMPLATE-001:** Шаблоны планов «на типовой день» без привязки к клиенту.

## Won’t (MVP)

- Оплаты и биллинг.
- **Публичная саморегистрация** тренера с открытой формы (**Sign up**) без участия админа.
- Личный кабинет **клиента** (посетителя зала), приглашения клиентов в приложение, OAuth **для клиентов**.
- Интеграции Apple Health / Google Fit.
- Офлайн-first синхронизация (если не будет отдельного решения).
- **Фунты / lb:** отдельные единицы и переключатель единиц — вне MVP (до появления явного требования).

## Критерии приёмки (ориентир)

Для Must: залогиненным пользователем с ролью **админа** **создать** учётку другого **тренера**; под учёткой с ролью **тренера** — **стартовать** тренировку с плана, довести до **завершения** (факт), сравнить с планом и с прошлой **завершённой** аналогичной; **параллельно** стартовать вторую тренировку у **другого** клиента, **переключаться** между текущими, завершить обе независимо; проверить **FACT-004** (не два `in_progress` у одного клиента). За ≤5 минут также: клиент с тегами, несколько будущих планов, история упражнения, быстрый выбор клиента (**UX-001**). Изоляция по `trainerId` и запрет админу читать чужой тренерский контент.
