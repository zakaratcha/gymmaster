# Технологии и данные

## Контекст

- **Только веб**, первый разработчик — один из тренеров.
- **Развёртывание (зафиксировано):** **один сервер** — backend (HTTP API) + **`SQLite`** (файл `*.db` на диске, без отдельного процесса СУБД). Клиент — **SPA** (одно приложение в браузере, данные через API); статика с того же хоста или CDN — без распределённого кластера в MVP.
- Нужны **аккаунты**, **сессии** и **изоляция** данных по `trainerId`; персистентность только на стороне сервера, не в «чистом браузерном файле» как единственном источнике правды.
- Репозиторий сейчас: пустой `package.json`; **backend** и **frontend** зафиксированы в разделе «Стек и ориентиры» ниже (**TypeScript** end-to-end: общие типы и часть кода между клиентом и сервером).

## Выбор СУБД

**Решение для MVP:** **SQLite** (файл на диске, просмотр через `sqlite3`/GUI, бэкап копированием файла с учётом режима **WAL**).

## Стек и ориентиры

- **Frontend (зафиксировано):** **React** + **TypeScript** + **MobX**.
- **Backend (зафиксировано):** **Node.js** + **TypeScript**; в разработке — **`ts-node`** (в проде — собранный вывод **`tsc`** или эквивалент). Монолитный HTTP API в одном процессе + **`SQLite`**. **Типы** и **часть кода** (например валидации, утилиты, доменные константы) — **общие** для клиента и сервера через единый пакет/каталог в одном репозитории. Миграции схемы — через выбранный ORM/утилиты. Фильтрация по **`trainerId`** в каждом запросе обязательна. **PostgreSQL / MongoDB** не входят в MVP до отдельного решения.
- **Auth:** **одна учётная запись** (`User`): **каждая** — **тренер** (`trainer` + **`trainerId`**). У **части** учёток дополнительно **`platform_admin`** (раздел администрирования в SPA); **выдать или снять** эту роль **нельзя** из приложения — см. **ADMIN-004** и **ADMIN-BOOT-001**. **Публичной регистрации** нет. **Одна сессия**; эндпоинты админки — по **`platform_admin`**, тренерский API — по **`trainerId`** текущего пользователя.

Критерий выбора **внутри** Node (HTTP-фреймворк, ORM, раскладка пакетов): скорость разработки одним человеком + безопасность изоляции тенантов + простота бэкапа одной БД.

## Доменная модель (черновик сущностей)

**Тренерские** данные (`Client`, `PlannedWorkout`, …) всегда содержат **`trainerId`** (идентификатор тенанта; у **каждого** пользователя в системе свой **`trainerId`**). **Администратор** к этим таблицам для чтения чужого контента **не** ходит. Запросы **тренерского** API всегда фильтруются по **`trainerId`** текущего пользователя.

| Сущность | Назначение |
|----------|------------|
| **User** | Единая учётка: email/login (глобально уникальный), хеш пароля, статус **активен/заблокирован**, опционально имя для UI, timestamps. **В системе только тренеры:** у **каждой** записи обязательны роль **`trainer`** и **`trainerId`** (суррогат тенанта; все `Client` / планы / сессии / `Exercise` ссылаются на него). Дополнительно у **части** пользователей — роль **`platform_admin`** (доступ к разделу администрирования). **Назначить или снять** `platform_admin` **нельзя** из интерфейса приложения — только **вне** его (bootstrap, миграция, CLI, конфиг деплоя; см. **ADMIN-004**, **ADMIN-BOOT-001**). **Новые** учётки тренеров создаёт пользователь с `platform_admin` из админ-раздела; публичного Sign up нет. |
| **Client** | Картотека клиента `trainerId`; опционально **пул известных тегов** для автодополнения. |
| **Exercise** | Упражнение в **личном** справочнике `trainerId` (название, опционально заметка, **`archivedAt`** или `isArchived`: если архивно — **не** в подборе для новых планов/фактов, но `exerciseId` в старых записях валиден). Вручную или **копия из сида** при **создании новой** учётки тренера из админ-раздела (в той же транзакции, что и `trainerId`). |
| **PlannedWorkout** | Будущий план: `trainerId`, `clientId`, **`plannedDate`**, **`splitTag`**, блоки упражнений. |
| **WorkoutSession** | Тренировка: `trainerId`, `clientId`, **`splitTag`**, **`status`**: `in_progress` \| `completed` (в MVP достаточно этих двух для потока «текущая → факт»), **`startedAt`**, **`completedAt`** (заполняется при завершении), опционально **`plannedWorkoutId`**. Блоки упражнений и подходы живут в сессии; **завершённая** сессия — то, что сравнивается с планом и попадает в историю. |
| **PlannedExercise / SessionExercise** | Строка упражнения в плане или факте с вложенными **подходами**: **вес в кг** (число), повторы, опционально отдых, RPE. |

**Вес:** одна размерность — **килограммы**; поле единицы измерения в схеме не вводить в MVP.

**Связь план ↔ сессия:** при старте с плана — `WorkoutSession.plannedWorkoutId` → `PlannedWorkout`; после **завершения** сессии план остаётся для сравнения **план ↔ факт** (статус плана «выполнен»/«снят» — опционально, можно выводить по наличию завершённой ссылки).

**Аналогичная прошлая тренировка:** последняя **WorkoutSession** со статусом **`completed`**, тем же `trainerId`, `clientId`, **`splitTag`**, `completedAt` строго раньше, чем у текущей сравниваемой **завершённой** сессии.

## Сид справочника упражнений

- В репозитории или миграции хранится **эталонный список** (JSON/CSV/таблица `exercise_seed`), **без** `trainerId`.
- При **создании** новой учётки с новым **`trainerId`** (из админ-раздела или bootstrap) транзакцией создаются копии строк в **`Exercise`** с этим `trainerId` (тот же контракт, что и у ручных записей).
- Состав сида версионируется в коде/миграциях; **существующие** аккаунты не перезаписываются автоматически при изменении сида (новым тренерам — новая версия сида).

## Интеграции

В MVP **не требуются** для доменной логики. **SMTP** может понадобиться позже для **AUTH-EMAIL-001** (Could); сброс пароля другой учётке в MVP — через пользователя с **`platform_admin`**.

## Открытые технические решения

- Конкретный провайдер писем, если включат **AUTH-EMAIL-001**.
- Одно устройство vs несколько — при необходимости refresh-токены и список сессий в «Could».
- Эволюция СУБД, если **SQLite** перестанет хватать (редкий случай для этого продукта).

**Сплит (зафиксировано):** свободные строковые **теги**; при желании нормализовать регистр при сохранении.
