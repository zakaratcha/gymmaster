# Технический проект

## Контекст

- Учётки лежат в таблице `trainers`: `id` (он же `trainerId`), уникальный `email`, `password` (bcrypt через `hashPassword`), `status` `active|blocked`, `admin` `0|1`. Роль `platform_admin` вычисляется в `trainerRoles` из `admin === 1`. Модели `Trainer`, `TrainerStatus` и `TrainerRole` лежат в `src/services/trainers/trainers.models.ts`.
- `requireAuth` отвечает 403 `{ error: 'forbidden' }` без cookie и при невалидной сессии. `findTrainerBySessionToken` уже отвергает сессию учётки со статусом не `active` и удаляет её. `login` отклоняет такую учётку ошибкой «Неверный логин или пароль». `revokeSessionsForTrainer` удаляет все сессии учётки.
- `seedExercisesForTrainer` асинхронный и вставляет сид отдельным запросом. Транзакции в проекте синхронные: `getSqlite().transaction(() => { db.insert(...).run(); })` (см. `plansService`). Асинхронный колбэк в транзакции better-sqlite3 не поддерживается.
- Тренерские маршруты фильтруют данные по `req.auth.trainerId`, чужой `id` даёт 404 `not_found`. Наличие `admin` на это не влияет.
- В SPA форма входа — состояние `App`, а не маршрут: после входа рендерятся `AppRoutes` для текущего адреса. `AppLayout` всегда рисует `ActiveWorkoutTabs` и запоминает путь в `workoutTabsStore`. `Shell` рисует нижнюю навигацию. Профиль `/account` сейчас умеет только выход.
- В транспорте `api` нет глобальной обработки 403, ошибки приходят как `ApiError` со `status`.
- API- и e2e-тесты ходят в работающий dev-сервер с постоянной БД, сброса БД между прогонами нет. Тестовые пользователи `Администратор` и `Тренер` зашиты в `testUsers.ts`.

## Ограничения

- Стек остаётся прежним: Express 5, drizzle-orm поверх better-sqlite3, React + MobX + react-router 7, cucumber + Playwright. Новых зависимостей нет.
- Пароли хранятся только через `hashPassword` и проверяются через `verifyPassword`.
- Схема БД не меняется: хватает существующих колонок `trainers`.
- Соблюдаются слои `service-layers`: client — только URL и вызовы, service без `http` и без импорта блоков. `*.models.ts` и `*.utils.ts` импортируют с `.ts`.
- Блоки по БЭМ, один компонент на файл, локальное состояние через `useLocalObservable`.
- Тесты не могут менять статус и пароль `first-admin@local` и `second-trainer@local`: от них зависят остальные сценарии.

## Решения

### Административный API в домене trainers

#### Решение

Роутер `src/server/trainers/trainersAdminRoutes.ts` монтируется в `apiRouter` на `/admin/trainers` с цепочкой `requireAuth` → `requirePlatformAdmin` (новый middleware в `src/server/middleware/`). Логика живёт в `trainersAdminService.ts`, проверка тел — в `trainerMapper.ts`. Контракт:

| Метод и путь                           | Тело                                | Успех                                                             | Ошибки                                |
| -------------------------------------- | ----------------------------------- | ----------------------------------------------------------------- | ------------------------------------- |
| `GET /api/admin/trainers`              | —                                   | 200 `{ trainers: AdminTrainer[] }` без текущей учётки, по `email` | 403                                   |
| `POST /api/admin/trainers`             | `{ email, password }`               | 201 `{ trainer: AdminTrainer }`                                   | 400 `{ error }`, 409 `{ error }`, 403 |
| `PATCH /api/admin/trainers/:id/status` | `{ status: 'active' \| 'blocked' }` | 200 `{ trainer: AdminTrainer }`                                   | 400, 404 `not_found`, 403             |
| `PUT /api/admin/trainers/:id/password` | `{ password }`                      | 204                                                               | 400, 404 `not_found`, 403             |

`AdminTrainer = { id, email, status }` — без ролей, пароля и дат. Прочие поля тела (`roles`, `admin`) игнорируются, `admin` при создании всегда `0`. Операции над `id === req.auth.trainerId` отвечают 400 `{ error: 'Нельзя изменить собственную учётку' }`. Тексты ошибок: «Проверьте введённые данные» для некорректного email, «Пароль должен быть не короче 8 символов», «Учётка с таким email уже существует».

#### Обоснование

Домен `trainers` уже есть и на сервере, и в `src/services`. Отдельный префикс `/admin` держит административные операции вне тренерских маршрутов, а единая проверка роли в middleware не позволит забыть её в отдельном обработчике. В `AdminTrainer` нет ролей, поэтому в API нет даже косвенного способа управлять `platform_admin`.

#### Рассмотренные альтернативы

- Проверять роль внутри каждого обработчика — легко пропустить на новом маршруте.
- Отвечать на чужие операции над собой 403 — это смешивается с «нет роли» и выглядит как потеря сессии.
- Генерировать временный пароль на сервере — пользователь просил, чтобы пароль задавал администратор.

#### Последствия

Возникает новый публичный контракт `/api/admin/trainers`. Учётка без роли получает 403 ещё до разбора тела, поэтому по ответу нельзя понять, существует ли учётка.

### Создание учётки одной синхронной транзакцией

#### Решение

Хэш пароля считается до транзакции. В `exerciseSeed.ts` выделяется функция, которая строит строки сида для `trainerId` и времени. Её используют и `seedExercisesForTrainer`, и создание. Создание проверяет занятость нормализованного email (`normalizeEmail`), затем в `getSqlite().transaction(() => …)` выполняет `insert(trainers).run()` и `insert(exercises).values(rows).run()`. Нарушение уникальности `email` в гонке (`SQLITE_CONSTRAINT_UNIQUE`) переводится в 409.

#### Обоснование

Сид и учётка коммитятся или откатываются вместе (**ADMIN-002**). bcrypt вне транзакции не держит блокировку записи. Общий построитель строк не даёт сиду бутстрапа и сиду админки разойтись.

#### Рассмотренные альтернативы

- Вызывать текущий асинхронный `seedExercisesForTrainer` после вставки учётки. Тогда при сбое сида остаётся учётка без справочника.
- Ловить только ошибку UNIQUE без предварительной проверки. Это работает, но смешивает ожидаемую ошибку с исключением в обычном пути.

#### Последствия

У `seedExercisesForTrainer` меняется только внутренняя сборка строк, поведение бутстрапа остаётся прежним.

### Блокировка и сброс пароля прекращают сессии

#### Решение

Смена статуса на `blocked` в одной транзакции обновляет `status` и `updatedAt` и удаляет сессии учётки. Сброс пароля в одной транзакции обновляет `password` новым хэшем и удаляет сессии. Разблокировка меняет только статус. Повторная установка того же статуса не считается ошибкой: учётка возвращается как есть.

#### Обоснование

`findTrainerBySessionToken` и так отвергает заблокированную учётку. Явное удаление сессий закрывает и сброс пароля: тот, кто знал старый пароль, теряет доступ сразу.

#### Рассмотренные альтернативы

Полагаться только на проверку статуса при каждом запросе — это не покрывает сброс пароля.

#### Последствия

После разблокировки тренер должен войти заново. Это ожидаемо.

### Общая проверка роли и правила пароля в моделях и утилитах trainers

#### Решение

В `trainers.models.ts` добавляются `AdminTrainer`, тела запросов и ответов и константа `MIN_TRAINER_PASSWORD_LENGTH = 8`. В новом `trainers.utils.ts` появляется чистая `isPlatformAdmin(roles)` с тестом `trainers.utils.test.ts`. Её используют middleware, гард маршрута и Профиль.

#### Обоснование

Одна проверка роли и одна граница длины пароля на сервере и в клиенте. Утилиты по правилам проекта покрываются `npm test`.

#### Рассмотренные альтернативы

Сравнивать `roles.includes('platform_admin')` по месту — это дублирование и риск опечатки.

#### Последствия

Утилита попадает и в серверный tsconfig, поэтому импорты в ней пишутся с `.ts`.

### Клиентские слои trainers

#### Решение

#### Обоснование

Это повторяет устройство остальных доменов и правило «компонент не ходит в http».

### Маршруты и шелл раздела вне AppLayout

#### Решение

В `AppRoutes` появляется ветка `/admin` того же уровня, что `AppLayout`, а не внутри него. Её элемент — блок `AdminLayout`. Он проверяет `isPlatformAdmin(currentUserStore.roles)` и без роли рендерит `<Navigate replace to='/clients' />`, не монтируя дочерние экраны. С ролью он рисует шапку «← Назад · Администрирование» и `Outlet`. «Назад» ведёт на `/account`. Дочерние маршруты: индекс `/admin` — блок `AdminTrainers` (список), `/admin/trainers/new` — блок `AdminTrainerCreateForm`, прочие `/admin/*` → `Navigate` на `/admin`. В `Profile` добавляется кнопка-ссылка «Администрирование» на `/admin`, видимая только при роли.

#### Обоснование

Вне `AppLayout` не рисуются полоса табов и нижняя навигация, не грузится `workoutTabsStore` и не запоминается путь админки как «Главная». Гард по роли работает и после входа с формы, поскольку `App` рендерит `AppRoutes` на тот же адрес уже с заполненным `currentUserStore`. Отдельной логики «после логина» не нужно.

#### Рассмотренные альтернативы

- Флаг в `AppLayout`, который прячет табы на `/admin`, — смешивает две витрины в одном лэйауте.
- Страница 403 — спецификация разрешает оба варианта, а пользователь выбрал редирект.

#### Последствия

Раздел администрирования не видит активных тренировок. Возврат в кабинет повторно загружает табы через `AppLayout`.

### Экраны раздела

#### Решение

`AdminTrainers` загружает список, показывает состояния загрузки, ошибки с повтором и пустого списка, кнопку «+ Создать» (переход на `/admin/trainers/new`) и строки «email · статус». В строке два действия: «Заблокировать» или «Разблокировать» по статусу и «Сбросить пароль». Вместо меню «···» из макета — явные кнопки в строке. Подтверждения сделаны на существующем блоке `Dialog`. Диалог сброса содержит поле нового временного пароля и кнопку подтверждения. После успеха то же диалоговое окно показывает пароль, а при закрытии значение стирается из локального состояния. Строки, их элементы, диалоги и форма — отдельные элементы БЭМ, каждый в своём файле. `AdminTrainerCreateForm` содержит поля Email и Пароль, подсказку о новом `trainerId` и копии сида, кнопку «Создать» и вывод текста ошибки сервера. После успеха выполняется переход на `/admin`. Состояние в обоих блоках — через `useLocalObservable`.

#### Обоснование

Явные кнопки проще для доступности и e2e-локаторов, чем выпадающее меню, а набор действий тот же. Пароль хранится только в состоянии открытого диалога, поэтому повторно его не показать.

#### Рассмотренные альтернативы

Отдельный экран результата сброса — лишний маршрут, а пароль попал бы в историю навигации.

#### Последствия

Если позже понадобится меню «···», меняется только разметка строки.

## Риски / Компромиссы

- Тесты блокируют или сбрасывают пароль у бутстрап-учёток, и соседние сценарии ломаются → все мутирующие сценарии работают только с учётками, созданными в самом сценарии.
- Постоянная БД копит тестовые учётки, а на занятом email возникают коллизии → уникальный email на сценарий (`trainer-<uuid>@local`). Список растёт, поэтому проверки ищут строку по email, а не по позиции.
- Временный пароль виден на экране администратора → он показывается только до закрытия диалога, нигде не сохраняется в открытом виде и не возвращается API.
- Гонка двух созданий с одним email → уникальный индекс БД и преобразование ошибки в 409.
- Администратор случайно блокирует себя → своей учётки нет в списке, API отвечает 400.

## План миграции и отката

Миграций схемы и данных нет. Выкатка — обычный деплой сервера и SPA. Откат — деплой предыдущей версии. Созданные через раздел учётки и их упражнения остаются валидными данными и при откате не мешают. Статусы `blocked`, выставленные через раздел, продолжают действовать.

## Стратегия проверки

- Модульные тесты (`npm test`): `isPlatformAdmin` для наборов ролей с ролью и без неё.
- API (`npm run test:api`, `tests/api/admin/`): 403 без сессии и от тренера без роли для списка и создания; создание возвращает активную учётку без `platform_admin`, даже если в теле передана роль; новый тренер входит и видит сид упражнений и пустой список клиентов; 409 на занятый email в другом регистре; 400 на короткий пароль; блокировка отклоняет вход и делает старую сессию недействительной (403 на список клиентов); разблокировка возвращает вход; после сброса вход проходит с новым паролем и не проходит со старым; операции над собой дают 400; список не содержит текущего администратора; администратор получает 404 на клиента `second-trainer@local` и не видит его в своём списке.
- E2E (`npm run test:e2e`, `tests/e2e/admin/`): администратор из Профиля открывает раздел, создаёт тренера, тот входит и видит сид упражнений и пустой список клиентов; администратор блокирует тренера с подтверждением, и вход этого тренера не проходит; тренер без роли по `/admin` попадает на `/clients`; в Профиле тренера нет пункта «Администрирование»; в разделе нет полосы табов и нижней навигации.
- Статический анализ: `npm run lint` (типы клиента, сервера и e2e, ESLint, stylelint, gherkin-lint).
