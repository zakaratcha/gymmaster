# Технический проект

## Контекст

- Тренерский API сессий живёт в `src/server/workoutSessions/`: маршруты `/api/clients/:clientId/workout-sessions` (`/active`, `/latest-completed`, `/:sessionId`, `/:sessionId/complete`), сервис на Drizzle + SQLite. Каждый запрос фильтруется по `trainerId` из `req.auth` и по `clientId`; чужая или несуществующая сессия даёт `undefined` → `404 not_found`.
- Публичная форма сессии — `WorkoutSession` из `src/services/workoutSessions/workoutSessions.models.ts` (общий тип клиента и сервера): `splitTag`, `status`, `startedAt`, `completedAt?`, `exercises[]` с `sets[]` (`reps`, `weightKg`), `plan`. Сборкой из строк БД занимаются `toPublicWorkoutSession` и `loadWorkoutSession`.
- У каждой сессии есть `splitTag`: при старте с плана он копируется из плана, без плана он обязателен. Тег приводится к виду без пробелов по краям (`trim`), регистр не нормализуется.
- `completedAt` записывается как `new Date().toISOString()`: строки одного формата в UTC, поэтому их лексикографический порядок совпадает с хронологическим. Выборка «последней завершённой» уже сортирует по `completedAt desc, startedAt desc, createdAt desc, id desc`.
- Индекс `idx_workout_sessions_trainer_client_status (trainerId, clientId, status)` покрывает фильтр по тренеру, клиенту и статусу.
- Сравнение план ↔ факт (CMP-001) собирается на клиенте чистой функцией `buildWorkoutComparison` из `workoutComparison.utils.ts`. Там же экспортирован `calculateVolumeKg`. Сопоставление повторов в CMP-001 устроено так: сначала точные пары подходов, затем первое свободное вхождение. Порядок строк задаёт план, внеплановые строки идут в конце.
- Форматирование — в `src/services/util/format.utils.ts`: `formatSetsText` («8×80 · 8×82.5 кг» или «—»), `formatVolumeKg`, `formatVolumeDeltaKg` («+20 кг», «-500 кг», «0 кг»), `formatSessionTimestamp` (дата со временем). Функции, которая выводит только дату сессии, нет.
- Экран `/workouts/:clientId/:sessionId` (блок `WorkoutSession`) смонтирован в `AppLayout` вне `Shell`. Для завершённой сессии он показывает `WorkoutComparison`, а без плана — ещё и список подходов.
- Тесты: юнит-тесты (vitest) для `*.utils.ts`, API-сценарии (cucumber, `tests/api/workout-sessions/workout-sessions.feature` + `tests/_harness/apiSteps/workoutSessions.steps.ts`), e2e (cucumber + Playwright, `tests/e2e/clients/*.feature`, объекты блоков в `tests/_harness/blocks/*`). E2E-шаг «для клиента … создана завершённая тренировка без плана с тегом …» уже создаёт и завершает сессию через API.

## Ограничения

- Стек: React + TypeScript + MobX на клиенте, Express + Drizzle + SQLite на сервере, общие типы в `src/services/*/*.models.ts`.
- Изоляция по `trainerId` обязательна в каждом запросе к сессиям.
- Правила проекта `.cursor/rules/*.mdc`: БЭМ-блоки и элементы по одному файлу, файл компонента экспортирует один компонент, локальное состояние через `useLocalObservable`, слои сервисов (`client`/`service`/`models`/`utils`), чистые функции в `*.utils.ts` с тестами `*.utils.test.ts`, импорты с `.ts` в файлах, которые проверяет серверный tsconfig, префикс `is` только у функций, Gherkin в порядке «Допустим → Когда → То».
- Сравнение план ↔ факт (CMP-001) не меняется ни по поведению, ни по коду.
- Схема БД не меняется.

## Решения

### Отдельный эндпоинт прошлой аналогичной сессии

#### Решение

`GET /api/clients/:clientId/workout-sessions/:sessionId/previous` → `200 { workoutSession: WorkoutSession | null }` (новый тип `WorkoutSessionPreviousResponse` в `workoutSessions.models.ts`).

- Текущая сессия читается по `id`, `clientId` и `trainerId`. Если её нет → `404 not_found`. Это покрывает чужого тренера, чужого клиента и несуществующую сессию.
- Если текущая сессия не `completed` или у неё нет `completedAt` → `{ workoutSession: null }`.
- Иначе выбирается одна строка: `trainerId` и `clientId` совпадают, `status = 'completed'`, `splitTag` равен тегу текущей, `completedAt < current.completedAt`, `id <> current.id`. Порядок — `completedAt desc, startedAt desc, createdAt desc, id desc`, `limit 1`. Найденная строка проходит через существующий `loadWorkoutSession`, поэтому форма ответа та же, что у остальных эндпоинтов сессий, вместе с полем `plan`.
- Без авторизации → `403 forbidden` от общего `requireAuth`, как у остальных маршрутов роутера.

#### Обоснование

Выбор прошлой сессии — серверное правило изоляции и сортировки: вся история клиента на клиент не приходит. Отдельный маршрут оставляет ответ `GET /:sessionId` без изменений, ответ лишь дополняется новым эндпоинтом. Ответ `200` с `null` повторяет соглашение `/active` и `/latest-completed`.

#### Рассмотренные альтернативы

- Вложить прошлую сессию в ответ `GET /:sessionId`. Это утяжеляет частый запрос и меняет его контракт.
- Отдавать список завершённых сессий и выбирать прошлую на клиенте. Такого эндпоинта нет, это тянет за собой историю (HIST-001) и лишние данные.
- Отвечать `404`, когда прошлой нет. Тогда «нет прошлой» не отличить от «нет сессии», и это расходится с `/latest-completed`.

#### Последствия

Экран завершённой сессии делает второй запрос. Поле `plan` прошлой сессии загружается, но в сравнении не используется — это допустимая цена единой формы ответа.

### Чистая сборка сравнения на клиенте в новом модуле

#### Решение

Новые файлы в `src/services/workoutSessions/`:

- `previousWorkoutComparison.models.ts`:
  - `PreviousWorkoutComparisonRow`: `exerciseId`, `exerciseName`, `previousText`, `currentText`, `previousVolumeKg`, `currentVolumeKg`;
  - `PreviousWorkoutComparison`: `rows`, `previousVolumeKg`, `currentVolumeKg`.
- `previousWorkoutComparison.utils.ts` с функцией `buildPreviousWorkoutComparison(previous, current)`. Алгоритм сопоставления вхождений:
  1. Проход по упражнениям текущей сессии по порядку: каждому даётся первое ещё не занятое вхождение прошлой сессии с тем же `exerciseId` и полностью равными подходами (та же длина, на каждой позиции совпадают `reps` и `weightKg`).
  2. Повторный проход по текущим упражнениям без пары: каждому даётся первое свободное вхождение прошлой сессии с тем же `exerciseId`.
  3. Строки идут в порядке текущей сессии: пара или строка «только текущая» с `previousText = '—'` и `previousVolumeKg = 0`. Затем по порядку прошлой сессии добавляются её незанятые вхождения с `currentText = '—'` и `currentVolumeKg = 0`.
  4. Имя строки берётся из текущего вхождения, а для строки «только прошлая» — из прошлого.

  Тексты подходов формирует `formatSetsText`, объём — `calculateVolumeKg`, импортированный из `workoutComparison.utils.ts` без изменений. Итоговые объёмы — суммы по всем упражнениям каждой сессии. Разницу (`current − previous`) вычисляет и форматирует UI через `formatVolumeDeltaKg`.

#### Обоснование

Логика та же, что в CMP-001: чистая функция, которую легко покрыть юнит-тестами. Сравнение с текущей сессией в роли «базы» даёт тренеру порядок сегодняшней тренировки. Отдельный модуль не трогает CMP-001, а это вне задачи.

#### Рассмотренные альтернативы

- Вызвать `buildWorkoutComparison`, подставив прошлую сессию как «план». Типы плана и сессии отличаются, статусы «не выполнено» и «вне плана» здесь не по смыслу, порядок задавала бы прошлая сессия.
- Вынести общий матчер и перевести на него CMP-001. Тогда меняется код план ↔ факт, а это вне задачи. Можно сделать отдельным рефакторингом позже.
- Сборка на сервере. Расходится с CMP-001, где сравнение собирается на клиенте, и ничего не даёт: обе сессии всё равно приходят на клиент.

#### Последствия

Правило «сначала точные пары, потом остаток» реализовано в двух местах. Расхождение ловят юнит-тесты обоих модулей.

### Дата сессии без времени

#### Решение

В `format.utils.ts` добавляется чистая `formatSessionDate(value: string): string`. Она переводит ISO-время в локальную дату `ДД.ММ.ГГГГ` (`Intl.DateTimeFormat('ru-RU', { day, month, year })`), а некорректную строку возвращает как есть, как `formatSessionTimestamp`. Используется в строке перехода и в заголовке экрана сравнения, всегда по `completedAt`.

#### Обоснование

В спецификации даты — без времени. Отдельная функция держит формат в одном месте и покрывается тестами.

#### Рассмотренные альтернативы

Обрезать результат `formatSessionTimestamp`. Это хрупко и зависит от формата локали.

#### Последствия

Дата показывается в часовом поясе браузера, как и остальные времена сессии.

### Переход на экране завершённой тренировки

#### Решение

- Клиентский слой: `workoutSessionsClient.getPrevious(clientId, sessionId)` без кэша и `getPreviousWorkoutSession(clientId, sessionId): Promise<WorkoutSession | null>` в `workoutSessions.service.ts`.
- `WorkoutSession` добавляет в локальный стор поле `previousSession: WorkoutSessionModel | null` и сеттер к нему. В `loadWorkout` прошлая сессия запрашивается параллельно с остальными данными, ошибка этого запроса гасится в `null`: переход не критичен для экрана.
- Новый элемент `WorkoutSession-Previous` (`src/blocks/WorkoutSession/Previous/`) рендерится для `completed`-сессии, когда `previousSession !== null`. Он выводится после блока сравнения и списка подходов: текст `С прошлой „<тег>“ (<дата>)` и `Link` «Подробнее» на `/workouts/:clientId/:sessionId/previous`. Значения в пути кодируются через `encodeURIComponent`.

#### Обоснование

Экран уже грузит данные в одном `loadWorkout`, а эндпоинт сам отвечает `null` для сессии в процессе. Отдельный элемент — по БЭМ-правилам проекта.

#### Рассмотренные альтернативы

Запрашивать прошлую сессию только после того, как текущая окажется завершённой. Это лишняя последовательная задержка при той же логике.

#### Последствия

Для сессии в процессе уходит лишний запрос с ответом `null`. Это дёшево.

### Отдельный экран сравнения

#### Решение

- Маршрут `/workouts/:clientId/:sessionId/previous` в `AppRoutes` рядом с маршрутом сессии, внутри `AppLayout`, вне `Shell`.
- Новый блок `src/blocks/PreviousWorkoutComparison/` (observer, `useLocalObservable`). Он загружает текущую сессию (`getWorkoutSession`) и прошлую (`getPreviousWorkoutSession`) параллельно и показывает состояния загрузки, ошибки с «Повторить» и «нет прошлой».
- Элементы в своих файлах:
  - `Header` — ссылка назад на `/workouts/:clientId/:sessionId` и заголовок `Сравнение: <тег>`;
  - `Dates` — `Текущая: <дата> · Прошлая: <дата>`;
  - `Summary` — строки «прошлая», «текущая» с объёмом в кг и «Δ объём»;
  - `List`, `Row` — название, «прошлая», «текущая», «Δ объём» строки;
  - `Empty`, `Loading`, `Error`.
- Блок `WorkoutComparison` не переиспользуется.
- «Нет прошлой» показывается, если ответ `null`: сессия не завершена или прошлой нет.

#### Обоснование

Экран — самостоятельная страница, а не часть дерева `WorkoutSession`, поэтому это отдельный блок. Блок `WorkoutComparison` завязан на модель план ↔ факт и её статусы, и его правка вне задачи.

#### Рассмотренные альтернативы

- Раскрывать сравнение внутри экрана сессии. Спецификация требует отдельный экран.
- Обобщить `WorkoutComparison`. Это меняет CMP-001.

#### Последствия

Часть стилей (строки «метка — значение») повторяется в новом блоке. Это осознанная плата за несвязанность двух сравнений.

## Риски / Компромиссы

- Две сессии с одинаковым `completedAt` до миллисекунды → условие «строго раньше» исключает такую сессию. Детерминированная сортировка `startedAt`, `createdAt`, `id` выбирает одну среди равных. В тестах сессии завершаются последовательными запросами.
- Сравнение `completedAt` строками → корректно, пока все значения пишет `toISOString()`. Иные значения не пишет никто, и это фиксируется в сервисе комментарием у запроса.
- Тег сравнивается точным равенством с учётом регистра, поэтому «Ноги» и «ноги» — разные теги → так данные уже хранятся. Нормализация регистра — отдельное решение (см. «Открытые вопросы»).
- Сопоставление дублируется с CMP-001 → оба модуля покрыты юнит-тестами на точную пару и остаток.
- Ошибка загрузки прошлой сессии на экране тренировки скрывает переход молча → экран сравнения при прямом входе показывает ошибку с «Повторить».

## План миграции и отката

- Миграции БД нет: схема и индексы не меняются.
- Выкатка — обычный деплой клиента и сервера вместе. Новый эндпоинт и маршрут только добавляются.
- Откат — возврат кода. Данные не затронуты, старый клиент не обращается к новому эндпоинту.

## Стратегия проверки

- Юнит-тесты (vitest):
  - `previousWorkoutComparison.utils.test.ts`: общее упражнение парой, упражнение только в текущей, только в прошлой; повтор упражнения, где точная пара важнее порядка; лишнее вхождение без пары; порядок строк (текущая, затем только прошлая); итоговые объёмы и пустые сессии.
  - `format.utils.test.ts`: `formatSessionDate` для корректного и некорректного значения.
- API-сценарии (cucumber, `workout-sessions.feature`):
  - выбирается последняя из нескольких прошлых с тем же тегом;
  - более поздняя сессия, сессия с другим тегом, сессия в процессе и сессия другого клиента не выбираются;
  - для первой сессии тега и для сессии в процессе приходит `null`;
  - сессия без плана получает прошлую с планом;
  - чужой тренер и несуществующая сессия → `404`, без авторизации → `403`.
- E2E (cucumber + Playwright, новый `tests/e2e/clients/previous-workout-comparison.feature` и объект блока `PreviousWorkoutComparison` в harness):
  - есть прошлая с тем же тегом → на экране завершённой тренировки видны «С прошлой „<тег>“» и «Подробнее», а экран сравнения показывает заголовок, сводку объёмов и строки с фактами и разницей;
  - прошлой нет → перехода нет;
  - прошлая только с другим тегом → перехода нет;
  - тренировка без плана → переход есть рядом с пояснением об отсутствии плана.
- Статический анализ: `npm run lint` (eslint, typecheck всех tsconfig, stylelint, gherkin-lint). Существующие юнит-, API- и e2e-тесты CMP-001 остаются зелёными.

## Открытые вопросы

- Нормализовать ли регистр тегов (`SPLIT-*`)? Пока сравнение точное, как хранится. Решение не влияет на этот подход.
