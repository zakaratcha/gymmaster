# Технический проект

## Контекст

- Маршруты `/login`, `/logout`, `/current-user` объявлены в `src/server/auth/authRoutes.ts`, логика — в `authService.ts`. Вход отвечает 200 и `{ ok: false, error }` на любую ошибку. Административные операции (`trainersAdminRoutes.ts`) отвечают 400 `{ error }` на ошибки проверки.
- `requireAuth` отвечает 403 `{ error: 'forbidden' }` без cookie и при недействительной сессии. В `req.auth` кладёт `trainerId`, `email`, `status`, `roles`, но не хэш пароля.
- `issueSession(trainerId, expectedPasswordHash)` в `sessionStore.ts` — синхронная транзакция better-sqlite3. Она перечитывает учётку, сверяет `status === 'active'` и хэш, удаляет все сессии учётки и вставляет новую. Сессия на учётку всегда одна: каждый вход снимает прежние. `setSessionCookie` экспортирован. Его поведение покрывает `sessionIssue.test.ts` на временной БД.
- Пароли хэшируются асинхронным bcrypt (`hashPassword`, `verifyPassword`). Асинхронный колбэк в транзакции better-sqlite3 не поддерживается. Вложенный вызов `transaction()` внутри транзакции выполняется как savepoint.
- Проверка пароля на длину и текст «Пароль должен быть не короче 8 символов» живут в `trainerMapper.ts` (`validatePassword`, `MIN_TRAINER_PASSWORD_LENGTH` из `trainers.models.ts`). Валидаторы тел экспортируются оттуда же.
- В SPA форму входа рисует `App`, когда в `currentUserStore` нет тренера. Маршрут `/account` (Профиль) лежит внутри `Shell`, а `Shell` — внутри `AppLayout`. В транспорте `api` нет глобальной обработки 403: ошибка приходит как `ApiError { status, body }`. Текст ошибки из `body.error` сейчас достаёт локальный хелпер блока `AdminTrainerCreateForm`.
- Выход из Профиля оставляет адрес `/account`: `logout` и `authenticate` в `auth.service.ts` маршрут не меняют, и после повторного входа показывается экран текущего адреса.
- API-шаги пишут ошибку запроса в общий `lastError` мира, а шаги входа и запроса текущего пользователя при успехе его очищают (`auth.steps.ts`, `adminTrainers.steps.ts`).
- Harness API хранит cookie сессий по email (`apiSession.ts`). `requestWithEmailSession` подставляет сохранённые cookie, но `Set-Cookie` из ответа не собирает: это умеет только `authClient.login` через `collectCookies`. Учётка сценария (`scenarioTrainer.ts`) одна на сценарий. Шаги `я выбираю пункт {string}` и `я выбираю {string}` в `AdminLayout.steps.ts` знают только «Администрирование» и «Назад».

## Ограничения

- Стек прежний, новых зависимостей и миграций БД нет.
- Хэш нового пароля считается только через `hashPassword`, текущий пароль проверяется через `verifyPassword`.
- Слои `service-layers`: клиент — URL и вызовы, сервис не вызывает `http` и не импортирует блоки, модели и утилиты импортируют с `.ts`.
- Блок по БЭМ, один компонент на файл, состояние через `useLocalObservable`, хендлеры в компоненте.
- Тесты меняют пароли только учёток, созданных в сценарии, и не трогают `first-admin@local` и `second-trainer@local`.

## Решения

### Контракт `PUT /api/current-user/password`

#### Решение

Маршрут объявляется в `authRoutes.ts` за `requireAuth`.

| Вход                                                                         | Ответ                                                      |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `{ currentPassword: string, newPassword: string }`                           | 204 + `Set-Cookie` новой сессии                            |
| поле не строка или пустая строка, тело не объект                             | 400 `{ error: 'Проверьте введённые данные' }`              |
| `newPassword` короче `MIN_TRAINER_PASSWORD_LENGTH`                           | 400 `{ error: 'Пароль должен быть не короче 8 символов' }` |
| `currentPassword` не совпадает с хэшем учётки                                | 400 `{ error: 'Неверный текущий пароль' }`                 |
| нет сессии, сессия недействительна или учётка заблокирована к моменту выдачи | 403 `{ error: 'forbidden' }`                               |

Учётка берётся только из `req.auth.trainerId`. Прочие поля тела (`id`, `trainerId`, `email`) не читаются. Валидатор `validateChangeOwnPasswordInput(body)` добавляется в `trainerMapper.ts` рядом с остальными и переиспользует `validatePassword`. Пустые строки проверяются до проверки длины, иначе пустой новый пароль получил бы текст о длине. Новый пароль, совпадающий с текущим, допустим: операция просто выдаёт новую сессию.

#### Обоснование

Ресурс «пароль текущего пользователя» лежит рядом с `/current-user` и по форме повторяет админский `PUT /admin/trainers/:id/password`, только без `id` в пути. Статус 400 на ошибки данных совпадает с административным API и с требованием 400 на короткий пароль. 403 остаётся только для «нет действующей сессии», поэтому клиент может однозначно перевести его в форму входа.

#### Рассмотренные альтернативы

- `POST /api/change-password` с ответом 200 `{ ok, error }`, как у входа, — противоречит требованию 400 на короткий пароль.
- 401 или 403 на неверный текущий пароль — клиент спутал бы его с потерей сессии.
- Ответ 200 с `trainer` — данные учётки не меняются, клиенту нечего обновлять.

#### Последствия

Появляется аддитивный публичный контракт. Тексты ошибок длины пароля у создания, сброса и смены совпадают, потому что берутся из одного валидатора.

### Замена хэша и выдача сессии одной синхронной транзакцией

#### Решение

`changeOwnPassword(auth, input)` в `authService.ts`:

1. читает строку учётки по `auth.trainerId`, пропущенную строку трактует как 403;
2. `verifyPassword(currentPassword, row.password)`, при неуспехе — 400 «Неверный текущий пароль»;
3. считает `newHash = await hashPassword(newPassword)` вне транзакции;
4. вызывает синхронную `replacePasswordAndIssueSession(trainerId, expectedHash, newHash)` из `sessionStore.ts`.

`replacePasswordAndIssueSession` в `getSqlite().transaction(...)` выполняет `update trainers set password = newHash, updatedAt = now where id = ? and password = expectedHash`. Если строк изменено 0, хэш сменился параллельно, и функция возвращает `{ ok: false, reason: 'stale' }`. Иначе внутри той же транзакции вызывается `issueSession(trainerId, newHash)`. Если она вернула `undefined` (учётка заблокирована), функция бросает внутреннее исключение, транзакция откатывается, и результат — `{ ok: false, reason: 'not-issued' }`. При успехе возвращается `{ ok: true, token }`. После коммита сервис вызывает `setSessionCookie(res, token)` из маршрута или сервиса. `stale` отдаётся как 400 «Неверный текущий пароль», `not-issued` — как 403.

#### Обоснование

Пароль и сессия меняются атомарно, как требует спека. Старая сессия удаляется тем же `issueSession`, поэтому правило «одна сессия на учётку» не дублируется. Условие `password = expectedHash` закрывает гонку со сбросом пароля администратором и параллельной сменой между `verifyPassword` и записью. bcrypt вне транзакции не держит блокировку записи.

#### Рассмотренные альтернативы

- Записать хэш, потом вызвать `createSession` отдельно — при сбое выдачи пароль уже сменён, а клиент без сессии.
- Расширить `issueSession` параметром «новый хэш» — это смешало бы вход и смену пароля в одной функции, а проверка `expectedPasswordHash` поменяла бы смысл.
- Вызывать `revokeSessionsForTrainer` вручную — дублирует то, что уже делает `issueSession`.

#### Последствия

Сессия, с которой пришёл запрос, удаляется. Клиент продолжает работу только с cookie из ответа: браузер подменяет её сам, а harness должен её собрать.

### Клиентские слои auth

#### Решение

- `auth.models.ts`: `ChangePasswordRequest { currentPassword, newPassword }`, форма экрана `ChangePasswordForm { currentPassword, newPassword, repeatPassword }`, `ChangePasswordResult = { ok: true } | { ok: false, error }`, константы `PASSWORD_MISMATCH_ERROR = 'Пароли не совпадают'` и общий текст на случай ошибки без тела.
- `auth.client.ts`: `changePassword(payload, config?)` — `api.put<void>` на `${apiUrl}/current-user/password`. Необязательный `config` с `collectCookies` нужен по образцу `login`.
- `api.utils.ts`: чистая `readApiErrorMessage(body: unknown): string | undefined` — достаёт непустую строку `body.error`. Покрывается `api.utils.test.ts`.
- `auth.service.ts`: `changeOwnPassword(form)`:
  - при `newPassword !== repeatPassword` возвращает `{ ok: false, error: PASSWORD_MISMATCH_ERROR }`, не вызывая клиент;
  - иначе вызывает `authClient.changePassword` и возвращает `{ ok: true }`;
  - `ApiError` 403 сбрасывает `currentUserStore` и `workoutTabsStore`, как `logout`, после чего `App` показывает форму входа;
  - прочие `ApiError` превращаются в `{ ok: false, error }` с текстом из `readApiErrorMessage`, иначе — общий текст.

#### Обоснование

Проверка повтора в сервисе гарантирует, что запрос не уйдёт, независимо от разметки. Блок получает готовый текст ошибки и не разбирает `ApiError` сам. Сервер возвращает человекочитаемые тексты, поэтому клиент их не переводит.

#### Рассмотренные альтернативы

- Сверять повтор в блоке — логика уходит в разметку, и её не переиспользовать.
- Перевести `AdminTrainerCreateForm` на `readApiErrorMessage` — полезно, но это вне границ изменения.

#### Последствия

Повтор пароля не уходит на сервер, а API принимает ровно два поля.

### Экран `PasswordChange` и пункт в Профиле

#### Решение

Новый блок `src/blocks/PasswordChange/PasswordChange.tsx` подключается маршрутом `/account/password` внутри `<Route element={<Shell />}>`. В нём:

- шапка с `Link` «←» на `/account` (`PasswordChange-Back`) и заголовком «Смена пароля»;
- три `Input type='password'` с подписями «Текущий пароль», «Новый пароль», «Повтор нового»;
- ошибка `role='alert'` (`PasswordChange-Error`), кнопка «Сохранить» (`type='submit'`) и `Loading`.

`PasswordChangeState` хранит три поля, `submitting` и `error`. При успехе блок делает `navigate('/account')`. Профиль получает `Button asChild` + `Link to='/account/password'` «Сменить пароль» (`Profile-PasswordChange`) для любой учётки, перед пунктом «Администрирование».

#### Обоснование

Экран повторяет устройство `AdminTrainerCreateForm` и остаётся в кабинете, как требует UI-спека. Отдельный маршрут, а не диалог, даёт адрес `/account/password` из спеки. Без сессии `App` и так рисует форму входа на любом адресе.

#### Рассмотренные альтернативы

- Диалог поверх Профиля — нет адреса `/account/password`.
- Экран вне `Shell` — у экрана Профиля и его подэкранов пропала бы нижняя навигация.

#### Последствия

Полоса активных тренировок остаётся над экраном, как на остальных экранах `AppLayout`. Её поведение не меняется.

### Harness: cookie новой сессии и вторая учётка сценария

#### Решение

- В `commands/auth/` появляется команда смены пароля через `authClient.changePassword` с `collectCookies`. Перед запросом она запоминает прежние cookie email-сессии как «запомненную сессию», а после успеха заменяет cookie в `cookiesByEmail` собранными из ответа. Результат смены хранится в отдельном поле мира `passwordChangeError` (`ApiError | undefined`), а не в `lastError`: сценарии проверяют отказ смены после входа или запроса текущего пользователя, а эти шаги очищают `lastError`. Отказ проверяют отдельные шаги `смена пароля через API отклонена с ошибкой {int}` и `… с ошибкой {int} и текстом {string}`, которые читают только `passwordChangeError`.
- Для тел с отсутствующим или нестроковым полем команда отправляет JSON из шага как есть, по образцу `я вхожу через API с телом JSON:`.
- В `scenarioTrainer.ts` добавляется вторая учётка сценария (B) со сбросом в тех же хуках. Для «чужого идентификатора» тело запроса дополняется `trainerId`, `id` и `email` учётки B: клиент принимает тело как есть, а harness формирует его явно.
- e2e-шаг «учётка сценария вошла на другом устройстве с паролем {string}» вызывает `loginWithCredentials` из Node. Это отдельный от браузера набор cookie, а `issueSession` снимает прежние сессии учётки, поэтому сессия браузера перестаёт действовать без перезагрузки страницы.
- В `AdminLayout.steps.ts` `я выбираю пункт {string}` начинает понимать «Сменить пароль», а `я выбираю {string}` — «←». Новые блоки `tests/_harness/blocks/PasswordChange/PasswordChange.block.ts` и `.steps.ts` описывают ввод полей, сохранение, ожидание ошибки и проверку адреса. В `Profile.block.ts` добавляется селектор `.Profile-PasswordChange`.

#### Обоснование

Без сбора `Set-Cookie` шаг «запрос с сессией из ответа» шёл бы со старым cookie и получал 403. Хранение прежнего cookie отдельно позволяет проверить, что он перестал действовать. Отдельное поле ошибки смены не даёт следующему шагу стереть проверяемый отказ. Вторая учётка не даёт трогать общие тестовые учётки. Вход с «другого устройства» — единственный способ прекратить сессию открытого экрана без участия UI и без перезагрузки, а значит дойти до обработки 403 в сервисе.

#### Рассмотренные альтернативы

- Проверять «чужой id» на `second-trainer@local` — при ошибке реализации сломался бы пароль общей учётки.
- Не очищать `lastError` в новых шагах входа и запроса текущего пользователя — проверка зависела бы от того, какие шаги идут после смены.
- Разделить сценарии «отказ» и «пароль и сессия прежние» — спека задаёт их одним сценарием, а следствие отказа без самого отказа не проверяет ничего.
- Прекращать сессию открытого экрана выходом через UI в другой вкладке — нужен второй контекст браузера ради того же эффекта.

#### Последствия

Тип тела в harness шире `ChangePasswordRequest`: TypeScript допускает лишние поля, если тело собрано в переменную.

## Обходы и допущения

- Новый пароль, равный текущему, разрешён — спека не запрещает, а это делает безопасным запрос Bruno.
- Гонка «хэш сменился между проверкой и записью» отвечает 400 «Неверный текущий пароль»: прежний текущий пароль к этому моменту действительно больше не действует.
- Учётка, заблокированная между проверкой сессии и выдачей новой, получает 403, а пароль остаётся прежним.
- Хелпер `readApiErrorMessage` в `AdminTrainerCreateForm` остаётся как есть: перевод на общую утилиту вне границ изменения.

## Риски / Компромиссы

- Выдача сессии в транзакции не удалась, а пароль записан → savepoint `issueSession` внутри внешней транзакции и исключение при `undefined` откатывают всё. Покрывается Vitest на временной БД.
- Клиент потерял ответ с новой cookie, а старая сессия уже удалена → тренер увидит форму входа и войдёт с новым паролем. Это допустимо, состояние данных при этом согласовано.
- Harness продолжает слать старую cookie после смены → команда смены всегда заменяет cookie email-сессии собранными из ответа, а сценарий «работа продолжается» это проверяет.
- Шаги `я выбираю {string}` и `я выбираю пункт {string}` растут ветками по тексту → допустимо для двух значений. Неизвестный текст по-прежнему бросает ошибку, и опечатка в .feature не проходит молча.

## План миграции и отката

Миграций данных и конфигурации нет. Откат — revert изменения: маршрут, экран и пункт Профиля исчезают, сменённые пароли остаются действительными хэшами bcrypt.

## Стратегия проверки

- `tests/api/auth/password.feature` (новый) покрывает требования API: без сессии 403; короткий пароль 400 с текстом и прежний пароль входит; `Структура сценария` по пустому текущему и пустому новому паролю — 400 «Проверьте введённые данные» и `current-user` в той же сессии 200; `Структура сценария` по телам с отсутствующим или нестроковым полем — 400 «Проверьте введённые данные» и прежний пароль входит; неверный текущий 400, `current-user` в той же сессии 200, прежний пароль входит; `current-user` с сессией из ответа 200; запомненная прежняя сессия 403; новый пароль входит, прежний отклоняется; чужой идентификатор в теле не меняет пароль учётки B. Все сценарии работают на учётках, созданных в сценарии.
- Новые шаги API (`apiSteps/auth.steps.ts` или новый `password.steps.ts`): создание учёток A и B, авторизация учётки сценария, смена пароля учётки сценария (с паролями из шага, с телом JSON, с чужими полями, без сессии), проверка отказа смены `смена пароля через API отклонена с ошибкой {int}` (с текстом и без) по `passwordChangeError`, запрос текущего пользователя в той же сессии, с сессией из ответа и с запомненной сессией, вход учётки сценария и учётки B с паролем. Проверки входа и запроса текущего пользователя переиспользуют `вход через API успешен`, `вход через API неуспешен с ошибкой {string}` и `API возвращает ошибку {int}`.
- `tests/e2e/auth/password.feature` (новый) покрывает требования UI: открытие экрана из Профиля и адрес; «←» возвращает в Профиль; несовпадение повтора показывает «Пароли не совпадают»; несовпадение не меняет пароль (выход и вход с прежним → Профиль с email: выход оставляет адрес `/account`); неверный текущий пароль показывает ошибку и экран остаётся; успех → Профиль с email и адрес `/account`; после смены и выхода новый пароль входит (Профиль с email), а прежний показывает «Неверный логин или пароль»; `/account/password` без сессии показывает форму входа; сессия, прекращённая входом той же учётки через API при открытом экране, после «Сохранить» приводит к форме входа — единственный сценарий, который доходит до обработки 403 в `auth.service.ts`. Учётка создаётся через API шагом `создана учётка сценария с паролем {string}` и входит через форму.
- Новые harness-блоки и шаги: `PasswordChange.block.ts` и `PasswordChange.steps.ts`, селектор пункта в `Profile.block.ts`, ветки «Сменить пароль» и «←» в шагах выбора, шаг «созданный тренер вошёл в приложение» без предварительного входа админа, если такого ещё нет, и шаг «учётка сценария вошла на другом устройстве с паролем {string}».
- Vitest `src/server/auth/passwordChange.test.ts` на временной БД, по образцу `sessionIssue.test.ts`, для `replacePasswordAndIssueSession` — только ветки гонок, недостижимые из приёмочных тестов: устаревший ожидаемый хэш не меняет ни хэш, ни сессии; у учётки, заблокированной к моменту выдачи, хэш и сессии прежние. Успешную замену хэша и сессии проверяют API-сценарии «Работа продолжается в новой сессии», «Прежняя сессия перестаёт действовать» и «Вход после смены пароля».
- Vitest `src/services/api/api.utils.test.ts` для `readApiErrorMessage` (`*.utils.ts` покрывается по `service-layers`) — только ветки без текста: пустая строка `error`, тело не объект, нет поля `error` → `undefined`. Сервер в сценариях изменения всегда отдаёт непустой `error`, поэтому эти ветки Gherkin не достигает. Чтение непустого текста проверяет e2e-сценарий «Неверный текущий пароль на экране».
