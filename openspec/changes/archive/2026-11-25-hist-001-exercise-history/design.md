# Технический проект

## Контекст

- Тренерский API сессий:
  - маршруты `/api/clients/:clientId/workout-sessions/*` в `src/server/workoutSessions/`, монтируются в `src/server/routes.ts`;
  - сервис `workoutSessionsService.ts` на Drizzle + SQLite. Каждый запрос фильтруется по `auth.trainerId`, а для чужих или несуществующих сущностей сервис возвращает `undefined`, что даёт `404 not_found`;
  - есть хелпер `hasClient(auth, clientId)`.
- Факт хранится в трёх таблицах:
  - `workout_sessions` со `status`, `completedAt` в ISO UTC и индексом `(trainer_id, client_id, status)`;
  - `session_exercises` с `exercise_id`, `position` и `trainer_id`; ссылка на `exercises` без каскада, поэтому архивное упражнение остаётся в прошлых сессиях;
  - `session_sets` с `reps`, `weight_kg` и `position`.
- Сохранение факта допускает упражнение с пустым `sets`.
- У упражнения в архиве заполнено `archivedAt`. `GET /api/exercises` без `includeArchived=true` отдаёт только рабочий список. `listExercises()` на клиенте по умолчанию тоже читает рабочий список.
- Экран `/workouts/:clientId/:sessionId` (блок `WorkoutSession`, вне `Shell`) один и для вкладки тренировки в процессе, и для завершённой сессии:
  - в процессе он показывает `WorkoutSessionForm` с карточками `WorkoutSession-ExerciseCard`. В заголовке карточки (`ExerciseHeader`) стоят «N. название» и `ExerciseActions`. Черновики факта (`drafts`) лежат в локальном сторе `WorkoutSession`;
  - для завершённой сессии он показывает блок `WorkoutComparison` (строки `WorkoutComparison-Row` с `exerciseId`), а без плана ещё и тот же список карточек без действий.
- Ни на вкладке, ни в данных нет понятия «текущее упражнение».
- Блок `Dialog` — модальный `<dialog>` с `showModal()`, закрывается через `onCancel`. Блок `ClientHub` (`/clients/:id`, внутри `Shell`) группирует разделы элементом `Section`. Раздела «История» сейчас нет.
- `workoutTabsStore.rememberPath` запоминает как путь основного интерфейса любой путь, кроме `/workouts/:clientId/:sessionId[/previous]`.
- Форматирование:
  - в `format.utils.ts` есть `formatWeightKg` («82.5») и `formatSessionDate` («ДД.ММ.ГГГГ»);
  - `formatSetsText` выводит «8×80 · 8×82.5 кг» — это другой формат, он используется в CMP-001 и CMP-002.
- Тесты:
  - vitest для `*.utils.ts`;
  - API-сценарии cucumber в `tests/api/*`;
  - e2e cucumber + Playwright в `tests/e2e/clients/*` с объектами блоков в `tests/_harness/blocks/*`. Готовые шаги создают завершённые тренировки через API.

## Ограничения

- Стек: React + TypeScript + MobX, Express + Drizzle + SQLite, общие типы в `src/services/*/*.models.ts`.
- Изоляция по `trainerId` во всех запросах. На чужой id отвечать так же, как на несуществующий.
- Правила `.cursor/rules/*.mdc`:
  - БЭМ: элемент — отдельный файл, один компонент на файл;
  - локальное состояние через `useLocalObservable`;
  - слои сервисов `client`/`service`/`models`/`utils`, чистые утилиты с `*.utils.test.ts`;
  - импорты с `.ts` в файлах, которые проверяет серверный tsconfig;
  - Gherkin в порядке «Допустим → Когда → То».
- Схема БД и миграции не меняются.
- Логика и тексты сравнений CMP-001 и CMP-002 не меняются. В строки `WorkoutComparison` добавляется только действие перехода.

## Решения

### Эндпоинт истории упражнения

#### Решение

`GET /api/clients/:clientId/exercise-history/:exerciseId` → `200 ExerciseHistoryResponse`:

- `clientName`;
- `exerciseName`;
- `entries[]`: `sessionId`, `completedAt`, `sets[]` (`reps`, `weightKg`).

Типы `ExerciseHistoryResponse` и `ExerciseHistoryEntry` лежат в новом `src/services/exerciseHistory/exerciseHistory.models.ts`.

- Новый роутер `exerciseHistoryRouter` в `src/server/exerciseHistory/exerciseHistoryRoutes.ts` с общим `requireAuth`, монтируется в `routes.ts` до `'/clients'`. Пустые id дают `400`.
- Сервис `exerciseHistoryService.ts`:
  1. Клиент читается по `id + trainerId`, упражнение — по `id + trainerId` без фильтра по `archivedAt`. Если чего-то нет → `undefined` → `404 not_found`.
  2. Один запрос с join `workout_sessions` ⋈ `session_exercises` ⋈ `session_sets` по `trainerId` текущего тренера, `clientId`, `status = 'completed'` и `exerciseId`. Сортировка: `completedAt desc, startedAt desc, createdAt desc, id desc`, затем `session_exercises.position asc`, `session_sets.position asc`.
  3. Строки группируются по сессии в порядке выборки. Подходы всех вхождений упражнения в сессии склеиваются по порядку. Inner join по подходам сам исключает сессии, где у упражнения нет подходов.
- Ответ не пагинируется.

#### Обоснование

Отбор и порядок — серверные правила изоляции, поэтому клиенту не нужно получать все сессии. Имена клиента и упражнения приходят в том же ответе: экран и модалка с одним запросом имеют одно состояние загрузки и одно состояние ошибки, а архивное упражнение не нужно искать в справочнике отдельно. Отдельный ресурс `exercise-history` не вклинивается в `workout-sessions/:sessionId` и не меняет его маршруты.

#### Рассмотренные альтернативы

- Отдавать список полных `WorkoutSession` и фильтровать на клиенте. Это лишние данные и дублирование правил отбора.
- `GET /api/exercises/:id/history?clientId=`. Тогда клиент становится фильтром, а не владельцем ресурса, и это расходится с остальными тренерскими маршрутами `/clients/:clientId/*`.
- Брать имена из `GET /clients/:id` и `GET /exercises/:id`. Это три запроса и три точки отказа на одном экране.

#### Последствия

Для клиента с очень длинной историей ответ растёт линейно. В MVP это допустимо, пагинацию можно добавить позже, не меняя формы строки.

### Сжатый формат подходов

#### Решение

Чистая `formatSetGroupsText(sets)` в `src/services/util/format.utils.ts`:

- подряд идущие подходы с равными `reps` и `weightKg` сворачиваются в «N×reps@вес», где вес выводится через `formatWeightKg`;
- группы соединяются « · »;
- пустой массив даёт «—».

Существующий `formatSetsText` не меняется.

#### Обоснование

Формат взят из макета истории и отличается от формата сравнений, поэтому для него нужна отдельная функция. Её легко покрыть юнит-тестами.

#### Рассмотренные альтернативы

Изменить `formatSetsText`. Тогда поменяются тексты CMP-001 и CMP-002, а это вне задачи.

#### Последствия

В проекте два формата подходов: сравнения и история.

### Блок истории, переиспользуемый на экране и в модалке

#### Решение

- Клиентский слой в домене `exerciseHistory`:
  - `exerciseHistory.client.ts` с `get(clientId, exerciseId)` без кэша;
  - `exerciseHistory.service.ts` с `getExerciseHistory(clientId, exerciseId)`.
- Блок `src/blocks/ExerciseHistory/`:
  - observer с `useLocalObservable`, пропсы `clientId`, `exerciseId`, `closeLabel` и `onClose()`;
  - загружает историю при монтировании и при смене id;
  - элементы: `Header` (кнопка «←» или «×» с `aria-label` из `closeLabel` и заголовок «История: <упражнение> · <клиент>»), `Table` с колонками «Дата» и «Подходы», `Row` (`formatSessionDate(completedAt)` и `formatSetGroupsText(sets)`), `Empty`, `Loading`, `Error` с «Повторить».
- Пока заголовок не загружен, `Header` показывает только кнопку закрытия.

#### Обоснование

Один блок закрывает и отдельный экран, и показ поверх вкладки. Единственное различие — что делает закрытие, и это передаётся пропсом.

#### Рассмотренные альтернативы

Два разных компонента для экрана и модалки. Это дублирование таблицы и состояний.

#### Последствия

Блок не читает параметры маршрута, это делает обёртка маршрута (следующее решение).

### Маршрут экрана истории

#### Решение

- Маршрут `/clients/:id/exercises/:exerciseId/history` внутри `Shell` (раздел клиента основного интерфейса). Элемент — `ExerciseHistoryScreen` в `src/blocks/ExerciseHistoryScreen/`: он читает `id` и `exerciseId` из `useParams` и рендерит `ExerciseHistory` с `closeLabel='Назад'`.
- Закрытие: если `location.key !== 'default'` (переход внутри приложения), то `navigate(-1)`. Иначе, при прямом входе, `navigate('/clients/:id')`.
- Id в путях кодируются через `encodeURIComponent`.

#### Обоснование

Экран открывается и с карточки (внутри `Shell`), и с экрана завершённой сессии (вне `Shell`). Возврат по истории браузера ведёт туда, откуда пришли, а прямая ссылка ведёт на карточку клиента. Путь вида `/clients/...` `workoutTabsStore` запоминает как путь основного интерфейса, и это корректно: история — часть кабинета.

#### Рассмотренные альтернативы

- Маршрут под `/workouts/...`. Тогда экран привязан к сессии, а вход с карточки сессии не имеет.
- Query-параметр `from` для возврата. Он дублирует то, что уже делает история браузера.

#### Последствия

Если открыть экран с завершённой сессии и нажать «←», вернёмся на сессию. Верхний таб «Главная» после этого указывает на экран истории, как и для любого другого экрана кабинета.

### Вход с карточки клиента

#### Решение

- В `ClientHub` появляется раздел `Section` «История» с кнопкой «История упражнения…».
- Нажатие открывает новый элемент `ClientHub-ExerciseHistoryDialog` на базе `Dialog`. Внутри:
  - рабочий список упражнений из `listExercises()` без архива;
  - состояния загрузки, ошибки с «Повторить» и «Справочник пуст»;
  - каждое упражнение — кнопка.
- Выбор закрывает диалог и делает `navigate('/clients/:id/exercises/:exerciseId/history')`. Состояние открытия диалога хранится в локальном сторе `ClientHub`, как у `StartDialog`.

#### Обоснование

Схема та же, что у выбора плана в `StartDialog`. Список кнопок проще и доступнее, чем `select` с отдельным подтверждением.

#### Рассмотренные альтернативы

Отдельный экран выбора упражнения. Это лишний маршрут ради одного шага.

#### Последствия

При каждом открытии диалога уходит запрос справочника. Это дёшево.

### Вход с экрана завершённой сессии

#### Решение

- `WorkoutComparison` получает необязательный проп `clientId`. Если он передан, `WorkoutComparison-Row` выводит в заголовке строки `Link` с `aria-label` «История упражнения <название>» на маршрут истории по `row.exerciseId`. Это касается всех статусов, включая «не выполнено».
- Сборка строк (`buildWorkoutComparison`) и статусы не меняются.
- `WorkoutSession-ExerciseCard` получает действие истории через новый элемент `WorkoutSession-ExerciseHistory` (иконочная кнопка «история» в `ExerciseHeader`). Для завершённой сессии без плана кнопка делает `navigate` на маршрут истории.

#### Обоснование

Обе строки — строки упражнения на экране завершённой сессии. Ссылка на маршрут даёт обычный переход с возвратом «←». Необязательный проп оставляет `WorkoutComparison` пригодным для мест без перехода.

#### Рассмотренные альтернативы

Открывать историю модалкой и на завершённой сессии. Это расходится с разделом 6 макета, где история — отдельный экран со стрелкой назад.

#### Последствия

Компонент строки CMP-001 получает новый необязательный проп. Его поведение без пропа не меняется.

### Вход с вкладки тренировки — модалка поверх вкладки

#### Решение

- Тот же элемент `WorkoutSession-ExerciseHistory` выводится в заголовке каждой карточки упражнения вкладки в процессе, рядом с `ExerciseActions`. Это `<button type="button">`, чтобы не отправлять `WorkoutSessionForm`.
- Нажатие записывает `historyExerciseId` в локальный стор `WorkoutSession`. Пока он задан, `WorkoutSession` рендерит `Dialog` с `ExerciseHistory` (`closeLabel='Закрыть'`). Закрытие через «×» или Esc сбрасывает `historyExerciseId`.
- Маршрут не меняется, поэтому `WorkoutSession` и его `drafts` остаются смонтированными. Несохранённый ввод не теряется, и автосохранение не трогается.
- Кнопка доступна и для упражнения, добавленного в черновик, но ещё не сохранённого: история читается по `exerciseId`, а сессия в процессе в неё не попадает по правилу сервера.

#### Обоснование

Модальный диалог поверх смонтированной вкладки — самый простой способ гарантировать, что состояние сессии не сбросится. Переход по маршруту размонтировал бы `WorkoutSession` с несохранёнными черновиками.

#### Рассмотренные альтернативы

- Отдельный маршрут поверх вкладки (background location). Это сложнее и рискует размонтировать форму.
- Нижний шит. Отдельного компонента для него нет, а `Dialog` уже есть и стилизован.

#### Последствия

На вкладке история открывается без отдельного URL, поэтому прямой ссылки на это состояние нет.

## Риски / Компромиссы

- Сессии с одинаковым `completedAt` → детерминированная сортировка `startedAt`, `createdAt`, `id`.
- Сравнение и сортировка `completedAt` строками → корректны, пока значения пишет `toISOString()`, как во всём сервисе.
- Join по подходам даёт много строк на длинной истории → данных мало (личный инструмент), а индексы по `(trainer_id, client_id, status)` и позициям уже есть. Пагинацию можно добавить позже.
- Иконочная кнопка внутри формы может отправить форму → `type="button"` и e2e-проверка, что ввод на вкладке сохраняется.
- Модальный `Dialog` поверх вкладки с таймером или автосохранением → вкладка остаётся смонтированной, её эффекты продолжают работать, и это ожидаемое поведение.

## План миграции и отката

- Миграции БД нет.
- Клиент и сервер выкатываются вместе. Эндпоинт, маршрут и действия только добавляются.
- Откат — возврат кода. Данные не затронуты.

  - дробный вес;

  - архивное упражнение сохраняет историю;
  - порядок от новых к старым, склейка повторов в одной сессии;
  - пустая история с именами;
  - `404` для чужого клиента, чужого и несуществующего упражнения;
  - `403` без авторизации.
- E2E (cucumber + Playwright, новый `tests/e2e/clients/exercise-history.feature` и объект блока `ExerciseHistory` в harness, расширение объектов `ClientHub`, `WorkoutSession` и `WorkoutComparison`):

  - вход из строки сравнения тренировки с планом и из списка тренировки без плана;
  - вход с вкладки: модалка со строкой прошлой тренировки; после закрытия введённый подход на месте;
  - пустая история;
  - ошибка загрузки и «Повторить» (ответ эндпоинта подменяется через `page.route`, как в объекте `ClientHub`).
- Статический анализ: `npm run lint`. Существующие юнит-, API- и e2e-тесты CMP-001, CMP-002 и вкладок остаются зелёными.
