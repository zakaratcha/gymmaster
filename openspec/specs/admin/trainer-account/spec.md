# admin/trainer-account Specification

## Purpose

Функциональность позволяет платформенному администратору сопровождать учётки других тренеров в отдельном разделе того же приложения. Администратор видит список учёток со статусом, создаёт тренера со стартовым справочником упражнений, блокирует и разблокирует учётки и сбрасывает пароль на временный. Чужие тренировочные данные раздел при этом не открывает.

## Requirements

### Requirement: Доступ к разделу администрирования

- **SHALL** раздел администрирования по маршруту `/admin` показывается только учётке с ролью `platform_admin`.
- **SHALL** учётка без роли `platform_admin`, которая открывает `/admin` или любой вложенный маршрут, перенаправляется на список клиентов `/clients`.
- **MUST NOT** при таком перенаправлении показываются данные раздела администрирования или сведения о других учётках.
- **SHALL** без сессии на `/admin` показывается форма входа, а после входа применяется то же правило доступа по роли.

#### Scenario: Администратор открывает раздел

- **GIVEN** тренер с ролью `platform_admin` вошёл в приложение
- **WHEN** он открывает `/admin`
- **THEN** показывается раздел администрирования со списком учёток тренеров

#### Scenario: Тренер без роли перенаправляется на клиентов

- **GIVEN** тренер без роли `platform_admin` вошёл в приложение
- **WHEN** он открывает `/admin`
- **THEN** показывается список клиентов
- **AND** адрес страницы — `/clients`

#### Scenario: Вход по ссылке в раздел без роли

- **GIVEN** сессии нет
- **AND** открыт адрес `/admin`
- **WHEN** тренер без роли `platform_admin` входит через форму входа
- **THEN** показывается список клиентов
- **AND** адрес страницы — `/clients`

### Requirement: Переход в раздел из Профиля

- **SHALL** в Профиле у учётки с ролью `platform_admin` есть пункт «Администрирование», который открывает раздел администрирования.
- **MUST NOT** пункт «Администрирование» показывается учётке без роли `platform_admin`.

#### Scenario: Пункт виден администратору

- **GIVEN** тренер с ролью `platform_admin` вошёл в приложение
- **WHEN** он открывает Профиль
- **THEN** в Профиле есть пункт «Администрирование»

#### Scenario: Пункт скрыт у тренера без роли

- **GIVEN** тренер без роли `platform_admin` вошёл в приложение
- **WHEN** он открывает Профиль
- **THEN** в Профиле нет пункта «Администрирование»

### Requirement: Шелл раздела администрирования

- **SHALL** раздел администрирования показывается в собственном шелле с заголовком «Администрирование» и действием «Назад».
- **SHALL** действие «Назад» возвращает в кабинет тренера.
- **MUST NOT** в разделе администрирования показываются полоса табов активных тренировок, нижняя навигация кабинета и контекст клиента.

#### Scenario: Полоса табов скрыта в разделе

- **GIVEN** у администратора есть тренировка в процессе
- **WHEN** он открывает раздел администрирования
- **THEN** полоса табов тренировок не показывается
- **AND** нижняя навигация кабинета не показывается

#### Scenario: Назад возвращает в кабинет

- **GIVEN** администратор открыл раздел администрирования
- **WHEN** он выбирает «Назад»
- **THEN** показывается кабинет тренера

### Requirement: Доступ к административному API

- **SHALL** административные операции над учётками тренеров без сессии отклоняются ответом 403.
- **SHALL** административные операции над учётками тренеров от учётки без роли `platform_admin` отклоняются ответом 403.
- **MUST NOT** отказ раскрывает данные учёток или факт их существования.

#### Scenario: Запрос без сессии

- **GIVEN** сессии нет
- **WHEN** выполняется запрос списка учёток тренеров
- **THEN** API возвращает ошибку 403

#### Scenario: Запрос тренера без роли

- **GIVEN** тренер без роли `platform_admin` авторизован в API
- **WHEN** он запрашивает список учёток тренеров
- **THEN** API возвращает ошибку 403

#### Scenario: Создание учётки тренером без роли

- **GIVEN** тренер без роли `platform_admin` авторизован в API
- **WHEN** он создаёт учётку тренера
- **THEN** API возвращает ошибку 403
- **AND** новая учётка не появляется

### Requirement: Список учёток тренеров

- **SHALL** список содержит учётки тренеров платформы, кроме учётки текущего администратора.
- **SHALL** для каждой учётки список показывает email и статус «активен» или «заблокирован».
- **MUST NOT** список и ответы административного API содержат пароли, хэши паролей, клиентов, планы и тренировки тренеров.

#### Scenario: Список показывает другие учётки со статусом

- **GIVEN** на платформе есть активная учётка `trainer-a@local` и заблокированная `trainer-b@local`
- **WHEN** администратор открывает раздел администрирования
- **THEN** список содержит `trainer-a@local` со статусом «активен»
- **AND** список содержит `trainer-b@local` со статусом «заблокирован»

#### Scenario: Своя учётка не в списке

- **GIVEN** администратор вошёл как `first-admin@local`
- **WHEN** он открывает раздел администрирования
- **THEN** список не содержит `first-admin@local`

### Requirement: Создание учётки тренера

- **SHALL** администратор создаёт учётку тренера по email и первоначальному паролю.
- **SHALL** создание добавляет активную тренерскую учётку с новым `trainerId`, и она появляется в списке со статусом «активен».
- **SHALL** новый тренер входит с заданными email и паролем.

#### Scenario: Создание через API

- **GIVEN** администратор авторизован в API
- **WHEN** он создаёт учётку с email `new-trainer@local` и паролем `secret-123`
- **THEN** ответ содержит учётку `new-trainer@local` со статусом «активен»
- **AND** у учётки только роль тренера

#### Scenario: Создание из раздела

- **GIVEN** администратор открыл форму «Новый тренер»
- **WHEN** он вводит email и пароль и выбирает «Создать»
- **THEN** показывается список учёток
- **AND** список содержит новую учётку со статусом «активен»

### Requirement: Стартовый справочник новой учётки

- **SHALL** создание учётки одной транзакцией копирует в её справочник стартовый набор упражнений.
- **SHALL** если любой шаг создания не удался, ни учётка, ни её упражнения не сохраняются.
- **SHALL** новый тренер после входа видит стартовый справочник упражнений и пустой список клиентов.

#### Scenario: Новый тренер получает стартовые упражнения

- **GIVEN** администратор создал учётку `new-trainer@local` с паролем `secret-123`
- **WHEN** новый тренер входит и открывает справочник упражнений
- **THEN** справочник содержит стартовый набор упражнений
- **AND** список клиентов пуст

### Requirement: Проверка данных при создании учётки

- **SHALL** создание отклоняется, если email некорректен или пароль короче 8 символов.
- **SHALL** создание отклоняется, если учётка с таким email уже существует; email сравнивается без учёта регистра и окружающих пробелов.
- **SHALL** при отказе форма показывает текст ошибки, а учётка и упражнения не создаются.

#### Scenario: Занятый email

- **GIVEN** администратор авторизован в API
- **WHEN** он создаёт учётку с email `Second-Trainer@local`
- **THEN** API отклоняет создание
- **AND** учёток с email `second-trainer@local` по-прежнему одна

#### Scenario: Короткий пароль

- **GIVEN** администратор авторизован в API
- **WHEN** он создаёт учётку с паролем `short`
- **THEN** API отклоняет создание с ошибкой проверки данных

### Requirement: Роль platform_admin не управляется из приложения

- **MUST NOT** создание учётки через API или UI назначает роль `platform_admin`, даже если запрос её содержит.
- **MUST NOT** административные операции API и UI меняют наличие роли `platform_admin` у существующей учётки.
- **MUST NOT** UI раздела содержит элементы назначения или снятия роли `platform_admin`.

#### Scenario: Попытка выдать роль при создании

- **GIVEN** администратор авторизован в API
- **WHEN** он создаёт учётку `wannabe-admin@local` с указанием роли `platform_admin` в запросе
- **THEN** созданная учётка не имеет роли `platform_admin`
- **AND** после входа как `wannabe-admin@local` раздел администрирования недоступен

### Requirement: Блокировка и разблокировка учётки

- **SHALL** администратор блокирует активную учётку и разблокирует заблокированную; в разделе каждое действие выполняется после подтверждения.
- **SHALL** после блокировки учётка не может войти, а её действующая сессия больше не принимается тренерским API.
- **SHALL** после разблокировки учётка снова входит со своим прежним паролем.
- **SHALL** после действия список показывает новый статус учётки.

#### Scenario: Заблокированный тренер не входит

- **GIVEN** администратор заблокировал учётку `new-trainer@local`
- **WHEN** тренер входит как `new-trainer@local` с верным паролем
- **THEN** вход отклоняется с ошибкой «Неверный логин или пароль»

#### Scenario: Сессия заблокированного тренера перестаёт действовать

- **GIVEN** тренер `new-trainer@local` авторизован в API
- **AND** администратор заблокировал его учётку
- **WHEN** тренер запрашивает список клиентов
- **THEN** API возвращает ошибку 403

#### Scenario: Разблокированный тренер снова входит

- **GIVEN** учётка `new-trainer@local` заблокирована
- **AND** администратор её разблокировал
- **WHEN** тренер входит как `new-trainer@local` с прежним паролем
- **THEN** вход успешен

#### Scenario: Отмена подтверждения блокировки

- **GIVEN** администратор выбрал «Заблокировать» у активной учётки
- **WHEN** он отменяет подтверждение
- **THEN** учётка остаётся со статусом «активен»

### Requirement: Сброс пароля учётки

- **SHALL** администратор задаёт учётке новый временный пароль; в разделе действие выполняется после подтверждения.
- **SHALL** временный пароль проходит ту же проверку длины, что и пароль при создании.
- **SHALL** после сброса учётка входит только с новым паролем, а её действующая сессия больше не принимается.

#### Scenario: Вход с временным паролем

- **GIVEN** администратор сбросил пароль `new-trainer@local` на `temp-pass-1`
- **WHEN** тренер входит как `new-trainer@local` с паролем `temp-pass-1`
- **THEN** вход успешен

#### Scenario: Старый пароль не действует

- **GIVEN** администратор сбросил пароль `new-trainer@local` с `secret-123` на `temp-pass-1`
- **WHEN** тренер входит как `new-trainer@local` с паролем `secret-123`
- **THEN** вход отклоняется с ошибкой «Неверный логин или пароль»

### Requirement: Однократный показ временного пароля

- **SHALL** после успешного сброса раздел один раз показывает временный пароль, чтобы администратор передал его тренеру.
- **MUST NOT** временный пароль снова показывается после закрытия сообщения или возвращается при чтении списка.

#### Scenario: Временный пароль показывается один раз

- **GIVEN** администратор подтвердил сброс пароля с временным паролем `temp-pass-1`
- **WHEN** сброс завершается успешно
- **THEN** раздел показывает временный пароль `temp-pass-1`
- **AND** после закрытия сообщения пароль больше не показывается

### Requirement: Своя учётка не сопровождается из раздела

- **MUST NOT** раздел предлагает блокировку и сброс пароля для учётки текущего администратора.
- **SHALL** API отклоняет блокировку, разблокировку и сброс пароля учётки текущего администратора, не меняя её.

#### Scenario: Блокировка себя через API

- **GIVEN** администратор `first-admin@local` авторизован в API
- **WHEN** он блокирует собственную учётку
- **THEN** API отклоняет операцию
- **AND** администратор по-прежнему авторизован

### Requirement: Изоляция тренировочных данных от администратора

- **MUST NOT** роль `platform_admin` даёт доступ к клиентам, планам и тренировкам другого `trainerId`.
- **SHALL** запрос администратора к клиенту другого тренера по его идентификатору отклоняется так же, как для любого тренера, без раскрытия факта существования.

#### Scenario: Администратор не читает чужого клиента

- **GIVEN** у тренера `second-trainer@local` есть клиент
- **AND** администратор `first-admin@local` авторизован в API
- **WHEN** администратор запрашивает этого клиента по идентификатору
- **THEN** API возвращает ошибку «не найдено»

#### Scenario: Список клиентов администратора без чужих клиентов

- **GIVEN** у тренера `second-trainer@local` есть клиент «Чужой клиент»
- **AND** администратор `first-admin@local` авторизован в API
- **WHEN** администратор запрашивает список клиентов
- **THEN** список не содержит «Чужой клиент»
